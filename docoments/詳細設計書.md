## 2. システム構成詳細
### 2-1. 全体構成
- FastAPIアプリケーションを起動し、その中でAPSchedulerを立ち上げる
- スケジュール実行と手動実行APIは同じ `DigestService` を呼び出す
- 永続化はSQLiteに集約する
- 外部連携はNewsAPI、OpenAI API、SMTPサーバーに限定する

### 2-4. 依存関係 / 責務分離方針
- API層はHTTP入出力だけを扱い、業務処理を持たない
- Service層は業務ルールを持ち、RepositoryとClientを組み合わせて処理する
- Repository層はSQL実行だけを担当し、外部API呼び出しを持たない
- Client層は外部システム通信だけを担当し、DB操作を持たない
- Schedulerは起動契機を提供するだけで、処理本体は `DigestService` に委譲する

## 3. 機能詳細設計
### 3-1. ニュース取得
- 機能概要: NewsAPIから指定分野の記事を最大20件取得する
- 利用者 / 実行主体: `DigestService`
- 入力値: ユーザー指定分野、取得上限 `20`、NewsAPIキー
- 出力値: `ArticleFetchResult` の配列
- 使用データ: NewsAPIレスポンス、設定値
- 正常処理:
1. `NewsService` が `NewsApiClient` を呼び出す
2. APIレスポンスからタイトル、説明文、URL、公開日時、配信元を抽出する
3. 必須項目不足のレコードを除外する
4. 取得件数を呼び出し元へ返す
- 異常処理:
1. APIキー未設定時は `ConfigurationError` を送出し、処理全体を中断する
2. HTTPエラー、タイムアウト、JSON不正時は `ExternalApiError` を送出し、実行履歴に失敗を記録する
- バリデーション:
  - `url` が空でないこと
  - `title` が空でないこと
  - `published_at` が日時として解釈可能であること
- ログ出力:
  - 取得開始
  - 取得成功件数
  - 取得失敗理由

### 3-2. 記事保存
- 機能概要: 取得記事をSQLiteへ保存し、URL重複を防ぐ
- 利用者 / 実行主体: `DigestService`
- 入力値: `ArticleFetchResult` の配列
- 出力値: 新規保存件数、既存スキップ件数
- 使用データ: `articles`
- 正常処理:
1. `ArticleRepository` がURL単位で存在確認またはUPSERT相当処理を行う
2. 未登録URLのみ新規保存する
3. `summary_status` は初期値 `pending` として登録する
- 異常処理:
1. DB接続失敗時は `DatabaseError` を送出し、処理全体を中断する
2. SQL実行失敗時はロールバックし、実行履歴へ失敗を記録する
- バリデーション:
  - URLの長さがDB許容範囲内であること
  - `published_at` がNULLでないこと
- ログ出力:
  - 保存開始
  - 新規保存件数
  - 重複スキップ件数
  - DBエラー内容

### 3-3. 記事選定
- 機能概要: 配信対象を最大5件に絞る
- 利用者 / 実行主体: `DigestService`
- 入力値: ユーザー指定分野、選定件数上限 `5`
- 出力値: 要約対象記事一覧
- 使用データ: `articles`
- 正常処理:
1. `ArticleRepository` からカテゴリ一致の記事を取得する
2. 公開日時降順で並べる
3. 上位5件を返す
- 異常処理:
1. DB読取失敗時は `DatabaseError` を送出する
2. 対象0件の場合は失敗ではなく配信スキップ扱いとする
- バリデーション:
  - `published_at` が存在する記事のみ対象とする
- ログ出力:
  - 選定開始
  - 選定件数
  - 対象0件の通知

### 3-4. AI要約
- 機能概要: 記事タイトルと説明文から日本語要約を生成する
- 利用者 / 実行主体: `DigestService`
- 入力値: 記事タイトル、説明文、URL
- 出力値: 記事ごとの要約結果
- 使用データ: `articles`、OpenAI APIレスポンス
- 正常処理:
1. `SummaryService` が対象記事を1件ずつ処理する
2. タイトルと説明文を要約用プロンプトへ整形する
3. `OpenAiClient` を呼び出し、2文から3文の日本語要約を受け取る
4. `articles.summary` と `summary_status=success` を更新する
- 異常処理:
1. 説明文が空の場合はタイトルのみで要約を試行する
2. API呼び出し失敗時は当該記事のみ `summary_status=failed` に更新する
3. 全件失敗時はメール送信を行わず、実行結果を `email_status=skipped` とする
- バリデーション:
  - タイトルが空のデータは要約対象から除外する
  - 要約結果が空文字の場合は失敗扱いとする
- ログ出力:
  - 要約開始
  - 記事単位の要約成功 / 失敗
  - 要約成功件数

### 3-5. メール本文生成
- 機能概要: 要約結果を配信メール本文へ整形する
- 利用者 / 実行主体: `DigestService`
- 入力値: 要約成功記事一覧、実行日時
- 出力値: 件名、本文
- 使用データ: 要約済み記事一覧
- 正常処理:
1. 件名を `指定分野ニュースダイジェスト YYYY-MM-DD` 形式で生成する
2. 本文へ各記事のタイトル、要約、URLを順番に並べる
3. 記事間に改行区切りを入れる
- 異常処理:
1. 要約成功記事が0件の場合は本文生成を行わない
2. 件名または本文の生成に必要なデータが欠落した場合は `MailBuildError` を送出する
- バリデーション:
  - URLを本文へ必ず含める
  - 件名は空文字を禁止する
- ログ出力:
  - 本文生成開始
  - 対象記事件数
  - 本文生成失敗理由

### 3-6. メール送信
- 機能概要: 固定配信先へプレーンテキストメールを送信する
- 利用者 / 実行主体: `DigestService`
- 入力値: 送信先アドレス、送信元アドレス、SMTP接続情報、件名、本文
- 出力値: 送信成否
- 使用データ: SMTP設定、`digest_runs`
- 正常処理:
1. `MailService` が設定値を検証する
2. `SmtpClient` でSMTP接続、認証、送信を実行する
3. 送信成功時は `digest_runs.email_status=success` を更新する
4. 配信対象記事の `last_sent_run_id` を更新する
- 異常処理:
1. SMTP設定不足時は `ConfigurationError` を送出する
2. 接続失敗、認証失敗、送信失敗時は `MailSendError` を送出する
3. 送信失敗時も要約結果は保持する
- バリデーション:
  - 送信先アドレス形式がメール形式であること
  - 本文が空でないこと
- ログ出力:
  - 送信開始
  - 送信成功
  - SMTPエラー内容

Gmail接続前提:
- `smtp.gmail.com` を利用する
- ポートは `587` を利用する
- 認証はGmailのアプリパスワードを利用する

### 3-7. 定期実行
- 機能概要: 毎日08:00にダイジェスト処理を起動する
- 利用者 / 実行主体: APScheduler
- 入力値: 実行時刻 `08:00`
- 出力値: ジョブ登録結果
- 使用データ: アプリ設定
- 正常処理:
1. アプリ起動時に `DigestScheduler` がジョブを登録する
2. 実行時に `DigestService.run(triggered_by="scheduler")` を呼び出す
- 異常処理:
1. スケジューラ初期化失敗時はアプリ起動失敗とする
2. ジョブ実行中の例外はログと実行履歴へ記録し、プロセスは継続する
- バリデーション:
  - 同一ジョブIDの重複登録を禁止する
- ログ出力:
  - ジョブ登録開始 / 完了
  - ジョブ実行開始 / 終了

### 3-8. 手動実行API
- 機能概要: ローカル検証用にバッチを即時実行する
- 利用者 / 実行主体: 開発者
- 入力値: HTTP POST `/jobs/digest/run`
- 出力値: 実行受付結果、実行ID、最終結果要約
- 使用データ: `digest_runs`
- 正常処理:
1. APIが `DigestService.run(triggered_by="manual")` を呼び出す
2. 実行結果をJSONで返す
- 異常処理:
1. 処理中例外発生時はHTTP 500を返す
2. 設定不備はHTTP 400を返す
- バリデーション:
  - リクエストボディは不要とする
- ログ出力:
  - 手動実行API受信
  - HTTP応答ステータス

補足:
- MVPではCLIを実装しない

### 3-9. ヘルスチェックAPI
- 機能概要: アプリ起動状態を確認する
- 利用者 / 実行主体: 開発者、レビュー担当者
- 入力値: HTTP GET `/health`
- 出力値: `status`, `app_name`, `timestamp`
- 使用データ: なし
- 正常処理:
1. 固定値 `status=ok` を返す
- 異常処理:
1. アプリ未起動時は応答しない。個別の異常処理は持たない
- バリデーション:
  - なし
- ログ出力:
  - リクエスト受信

### 3-10. 直近実行結果取得API
- 機能概要: 直近のダイジェスト実行結果を返す
- 利用者 / 実行主体: 開発者
- 入力値: HTTP GET `/jobs/digest/runs/latest`
- 出力値: 実行ID、開始時刻、終了時刻、件数、メール送信結果、エラー内容
- 使用データ: `digest_runs`
- 正常処理:
1. `DigestRunRepository` から最新1件を取得する
2. JSONへ整形して返す
- 異常処理:
1. 実行履歴が0件の場合は空レスポンスではなくHTTP 404を返す
2. DB読取失敗時はHTTP 500を返す
- バリデーション:
  - なし
- ログ出力:
  - 参照API受信
  - 応答結果

- スキーマ変更は `schema.sql` 更新とDB再作成で対応する

## 7. バッチ / 定期処理設計（必要時）
### 7-1. 実行単位
- 1ジョブ = ニュース取得からメール送信までの一連処理
- 実行識別子は `digest_runs.id` を利用する

### 7-2. 実行シーケンス
1. 実行開始レコード作成
2. ニュース取得
3. 記事保存
4. 記事選定
5. AI要約
6. メール本文生成
7. メール送信
8. 実行結果更新
9. 終了ログ出力

### 7-3. 再実行方針
- 手動実行APIで同日に複数回再実行可能とする
- URL重複により記事二重登録は行わない
- 再実行時も最新記事から再選定する

### 7-4. 排他方針
- MVPでは単一プロセス運用とする
- 同時実行防止のため、ジョブ起動前にアプリ内フラグまたはロックを確認する
- 実行中に新規手動実行要求が来た場合はHTTP 409を返す前提とする

## 8. クラス設計 / 責務分割
| クラス / コンポーネント | 主責務 | 主なメソッド |
|------|------|------|
| `Settings` | 環境変数読み込み、必須設定検証 | `validate()` |
| `DigestService` | 全体処理統括、処理順序制御、実行結果集約 | `run(triggered_by)` |
| `NewsService` | ニュース取得業務ルール | `fetch_latest_articles()` |
| `ArticleSelector` | 記事選定ルール | `select_top_articles(articles, limit)` |
| `SummaryService` | 要約生成と結果更新 | `summarize_articles(run_id, articles)` |
| `MailService` | 件名本文生成、送信制御 | `build_message()`, `send_message()` |
| `RunHistoryService` | 実行開始、完了、失敗更新 | `start_run()`, `finish_run()`, `fail_run()` |
| `ArticleRepository` | 記事の登録、更新、取得 | `save_articles()`, `get_recent_articles()`, `update_summary()`, `mark_sent()` |
| `DigestRunRepository` | 実行履歴操作 | `create_run()`, `update_result()`, `get_latest()` |
| `NewsApiClient` | NewsAPI通信 | `fetch_news(category, page_size)` |
| `OpenAiClient` | OpenAI API通信 | `summarize(title, description)` |
| `SmtpClient` | SMTP送信 | `send(subject, body, to_address)` |
| `DigestScheduler` | APSchedulerジョブ登録 | `register_jobs()` |

責務分割ルール:
- 要約文生成プロンプトは `SummaryService` に置き、Controller層へ持ち込まない
- SQL文はRepository層に閉じ込める
- 外部APIのレスポンス整形はClient層で完結させる
- `DigestService` は個別SQLやHTTP通信を直接持たない

## 9. エラー設計
### 9-1. 例外分類
| 例外名 | 発生箇所 | 影響範囲 | API応答 | 処理方針 |
|------|------|------|------|------|
| `ConfigurationError` | 設定読込、メール送信前 | 全体 | 400 | 実行中断 |
| `DatabaseError` | Repository | 全体 | 500 | 実行中断 |
| `ExternalApiError` | NewsAPI、OpenAI API | 記事単位または全体 | 500 | NewsAPIは中断、OpenAIは記事単位失敗 |
| `MailBuildError` | メール本文生成 | 全体 | 500 | 実行中断 |
| `MailSendError` | SMTP送信 | 全体 | 500 | 実行終了、送信失敗記録 |
| `JobAlreadyRunningError` | 手動実行API、Scheduler | 単一要求 | 409 | 新規実行拒否 |

### 9-2. 異常時の更新方針
- 全体中断系エラーでは `digest_runs.finished_at` と `error_message` を更新する
- 記事単位エラーでは `articles.summary_status=failed` を更新し、全体処理は継続する
- メール送信失敗時は `digest_runs.email_status=failed` を記録する

## 10. ログ設計
### 10-1. ログ方針
- ログレベルは `INFO`, `WARNING`, `ERROR` を使用する
- 出力先はファイルと標準出力の両方とする
- 1実行を追跡できるよう `run_id` を全主要ログへ含める

### 10-2. 主なログ項目
| ログイベント | レベル | 必須項目 |
|------|------|------|
| アプリ起動 | INFO | timestamp |
| 設定検証失敗 | ERROR | field_name, reason |
| ニュース取得開始 / 終了 | INFO | run_id, category, count |
| 記事保存結果 | INFO | run_id, inserted_count, skipped_count |
| 要約失敗 | WARNING | run_id, article_url, reason |
| メール送信成功 | INFO | run_id, to_address |
| メール送信失敗 | ERROR | run_id, reason |
| 実行全体失敗 | ERROR | run_id, step_name, reason |

## 11. セキュリティ設計
- APIキー、SMTPユーザー名、SMTPパスワード、送信先アドレスは環境変数で取得する
- `.env` を使う場合はGit管理対象外とする
- APIはローカル利用に限定し、`0.0.0.0` で外部公開する前提を置かない
- 認証は実装しないが、将来公開時にルーター単位で認証追加できる構成とする
- ログへAPIキー、SMTPパスワード、OpenAI生レスポンスを出力しない
- メール本文へ保存済み要約のみを利用し、外部入力をそのままSMTPヘッダへ使わない

## 12. 性能・運用設計
- 同期処理で十分成立するため、非同期ジョブキューは導入しない
- 取得20件、要約5件の上限を超える処理はMVPでは行わない
- Docker実行時はSQLiteファイルとログファイルをホストへマウントできる構成を想定する
- アプリ再起動でスケジューラは再登録される
- PC停止中の未実行ジョブを自動補填する仕組みは持たない
- API手動実行で検証、障害復旧、再送確認を行う
