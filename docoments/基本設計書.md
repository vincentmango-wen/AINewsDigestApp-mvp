# 基本設計書

## 0. 前提・スコープ
### 0-1. 要件から確定している事項
- システム名はFocusDigestとする
- MVPの主目的は、ニュース取得、記事選定、AI要約、メール送信、定期実行を一連で成立させることである
- 対象分野はユーザーが事前に指定した1件とする
- ニュース取得元はNewsAPIを利用する
- 要約はOpenAI APIを利用する
- 保存先DBはSQLiteとする
- メール送信はSMTPを利用する
- 定期実行はAPSchedulerを利用し、毎日08:00に実行する
- 配信先メールアドレスは1件固定とする
- Web UI、認証、複数ユーザー対応、クラウド本番運用はMVP対象外である

### 0-2. 設計上の前提
- 本システムは個人開発のMVPであり、利用者は開発者本人またはレビュー担当者を想定する
- 運用環境はローカルPCまたはDocker起動環境とし、常時稼働サーバーは前提にしない
- NewsAPIから取得できる記事情報はタイトル、説明文、URL、公開日時、配信元とする
- AI要約の入力は記事本文ではなく、タイトルと説明文の組み合わせとする
- FastAPIは将来拡張の土台として採用し、MVPでは手動実行確認とヘルスチェックのための最小APIのみ提供する
- SMTPは外部メールサービスのSMTP接続を利用する前提とし、送信元アカウント管理画面は持たない
- SMTP接続先はGmailとし、認証にはGmailのアプリパスワードを利用する
- 環境変数管理は `.env` の利用を許容する
- SQLiteファイルは `data/app.db` に保存し、ログファイルは `logs/app.log` に保存する
- Docker利用時は `./data:/app/data` と `./logs:/app/logs` をホストマウントする
- 手動実行手段はFastAPIのHTTP APIのみとする
- `digest_runs` にはメール本文を保存せず、送信結果のみ保存する
- 分野名は `2文字以上50文字以内` とし、日本語、英字、数字、半角スペース、`-`、`_` を許可する
- 分野設定値は保存前に前後空白を除去し、連続空白は1個に正規化する
- 分野設定はMVPでは1件のみ保持する
- DBバックアップは日次1回、14世代保持とする
- ログは日次ローテーションし、30日保持する

### 0-3. 設計対象範囲
- ニュース取得バッチ処理
- 記事保存処理
- 記事選定処理
- AI要約処理
- メール本文生成と送信処理
- 日次スケジューラ起動
- 実行結果ログ出力
- 手動確認用API

### 0-4. 今回対象外とする範囲
- 一般利用者向け画面
- 管理画面
- ユーザー認証、認可、権限管理
- 複数カテゴリ設定
- 複数配信先管理
- ニュース本文スクレイピング
- HTMLメール
- クラウドデプロイ
- 監視基盤連携
- CI/CD構築

## 1. システム概要
- システム名: FocusDigest
- 目的: ユーザーが指定した分野のニュースを日次で収集し、AIで要点を日本語要約してメール配信する
- 解決する課題: 複数ニュースを個別に確認する手間を減らし、短時間で主要トピックを把握できるようにする
- 想定ユーザー: 開発者本人、ポートフォリオ閲覧者、レビュー担当者
- 利用シーン: 毎朝の情報収集、API連携とAI要約の実装実績の提示、面接時の成果説明

## 6. API設計（対象がある場合のみ）
| Method | Endpoint | 説明 | 認証 |
|--------|----------|------|------|
| GET | /health | アプリケーションの起動確認を返す | なし |
| POST | /jobs/digest/run | ニュース取得からメール送信までを手動実行する | なし |
| GET | /jobs/digest/runs/latest | 直近実行結果を返す | なし |

対象APIはローカル確認用途に限定する。

外部公開や一般利用者アクセスは想定しないため、認証は導入しない。
手動実行は `POST /jobs/digest/run` に一本化する。

## 7. 業務フロー / 処理フロー
1. FastAPIアプリケーションが起動し、設定値と環境変数を読み込む
2. アプリ起動時にAPSchedulerへ日次08:00のジョブを登録する
3. スケジュール実行または手動実行APIによりダイジェスト処理を開始する
4. 実行履歴を `digest_runs` に開始状態で登録する
5. NewsAPIから指定分野の記事を最大20件取得する
6. 取得した記事を `articles` へ保存する。URLが既存の場合は新規登録しない
7. 保存済み記事から公開日時順で最大5件を選定する
8. 各記事のタイトルと説明文をOpenAI APIへ渡し、日本語要約を生成する
9. 要約成功分を `articles.summary` に保存し、失敗分は `summary_status=failed` とする
10. 要約成功記事が1件以上ある場合はメール本文を生成する
11. SMTPサーバーへ接続し、固定送信先へプレーンテキストメールを送信する
12. 実行結果を `digest_runs` に反映し、件数と成否を更新する
13. 各処理の開始、終了、件数、例外内容をログファイルへ出力する
14. 途中失敗時は失敗箇所をログと実行履歴に記録し、その回の処理を終了する

## 8. 非機能要件
| 項目 | 内容 |
|------|------|
| 性能 | 1日1回のバッチ実行を前提とし、20件取得、5件要約、1通送信が数分以内に完了することを目標とする |
| セキュリティ | APIキー、SMTP接続情報、送信先アドレスは環境変数または.envで管理し、ソースコードへ埋め込まない |
| 可用性 | 常時稼働保証は行わない。起動中の環境で日次ジョブが正常実行されることを要件とする |
| 保守性 | 取得、保存、選定、要約、送信、スケジューラをモジュール分割し、単一責務で管理する |
| 拡張性 | MVPでは単一分野、単一配信先に固定するが、DBと処理分割により後続で分野追加しやすい構成とする |
| 監視・運用 | 外部監視は導入しない。ログファイル確認と直近実行履歴確認APIを最低ラインとする |

## 9. 技術スタック提案
- Frontend:
  - 採用技術: なし
  - 採用理由: MVPでは利用者向け画面を持たず、実装対象をバッチ処理と外部連携に集中させるため
- Backend:
  - 採用技術: Python 3.x + FastAPI + APScheduler
  - 採用理由: Pythonで外部API連携とバッチ処理をまとめて実装しやすく、FastAPIで手動確認用APIも同一アプリ内に収められるため
- DB:
  - 採用技術: SQLite
  - 採用理由: セットアップ不要でローカル完結でき、MVP規模のデータ量に十分対応できるため
- Infra:
  - 採用技術: Docker
  - 採用理由: ローカル差異を抑えて再現性を確保し、レビュー担当者が起動しやすくなるため

- SQLite保存
- 最大5件の記事選定
- OpenAI APIによる日本語要約
- SMTPメール送信

### 10-2. 後続フェーズに回す機能

- 認証機能
- クラウド常時運用
- HTMLメール

### 10-3. MVP時の構成簡略化方針
- 単一アプリケーション構成とし、APIサーバーとジョブワーカーを分離しない
- DBはSQLite固定とし、RDBMS移行は後続フェーズとする
- 認証は導入しない
- 外部連携はNewsAPI、OpenAI API、SMTPの3つに限定する
- キュー基盤や非同期ワーカーは導入しない

## 11. リスク・懸念点
| 項目 | 内容 | 対策 |
|------|------|------|
| NewsAPI依存 | 取得上限やレスポンス内容変更でニュース取得が不安定になる可能性がある | 失敗時ログを残し、取得処理を分離して差し替え可能にする |
| OpenAI API失敗 | 要約APIの失敗でメール本文が作れない可能性がある | 記事単位で失敗を記録し、全件失敗時のみ送信を中止する |
| SMTP設定不備 | 認証失敗や接続制限で送信できない可能性がある | 起動前設定チェックと送信失敗ログを整備する |
| ローカル運用 | PC停止中は定期実行されない | MVPでは手動実行APIによる再実行で補完し、常時運用は対象外とする |
| 認証なしAPI | ローカル外へ公開すると不正実行のリスクがある | ローカル利用に限定し、外部公開しない前提を明記する |
| SQLite制約 | 同時アクセスが増えると運用しづらい | MVPは単一プロセス、低頻度実行に限定する |

## 12. 確認事項
- 1記事の複数回配信履歴を将来保持する必要があるか確認する必要がある
- 将来外部公開時の認証方式、HTTPS終端、Rate Limit方針を確認する必要がある
