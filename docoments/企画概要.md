# 企画概要

## 1. 企画名
- FocusDigest

## 2. 企画の背景
- 分野ごとのニュースは更新頻度が高く、情報源が分散している
- 情報収集のたびに複数サイトを確認すると、読む時間より探す時間が増える
- ポートフォリオとしては、単なるCRUDではなく、外部API連携、AI活用、定期実行、通知まで一連で実装された成果物の方が説明価値が高い
- 既存資料では要件、設計、アーキテクチャは整理済みだが、企画目的、成功基準、優先順位、進め方をまとめた上位文書が不足していた

## 3. 企画の目的
- AI活用アプリを1本完成させ、ポートフォリオとして提示できる状態にする
- Pythonによるバックエンド実装力、外部API連携力、バッチ処理設計力を示す
- ユーザーが指定した分野のニュース取得から要約、保存、メール送信までの業務フローを一気通貫で成立させる
- 面接やレビューで「なぜこの機能だけに絞ったか」を説明できる成果物にする

## 4. 解決したい課題
| 課題 | 現状 | 解決方針 |
|------|------|----------|
| 情報収集に時間がかかる | 関心分野ごとに複数ニュースを個別に開いて確認する必要がある | ユーザーが指定した分野の主要ニュースを収集し、要約して1通のメールに集約する |
| AIアプリの開発経験を示しにくい | 単機能デモでは実務イメージが伝わりにくい | API連携、AI要約、定期実行、通知を組み合わせる |
| 初学者が作り切れずに破綻しやすい | 画面、認証、クラウド運用まで広げると工数が膨らむ | MVPではバックエンドと定期バッチに集中する |

## 5. 想定ユーザー
| ユーザー | 利用目的 |
|------|----------|
| 開発者本人 | 指定した分野のニュースを短時間で把握する |
| ポートフォリオ閲覧者 | アプリ全体の構成と実装範囲を確認する |
| 面接官・レビュー担当者 | 技術選定、責務分離、失敗時設計を評価する |

## 6. 提供価値
- 毎日1回、ユーザーが指定した分野のニュース要点をまとめて受け取れる
- 取得、保存、要約、送信の流れがつながった実装として説明できる
- MVP段階でも「動く成果物」として再現しやすい
- 将来、Web UIや複数配信先追加、分野設定機能へ拡張できる土台になる

## 7. 今回のMVPで実現すること
- ユーザーが事前に指定した1つの分野に関するニュースをNewsAPIから取得する
- 取得した記事をSQLiteへ保存する
- 公開日時順で上位5件を選定する
- OpenAI APIで日本語要約を生成する
- 要約結果をプレーンテキストメールで1件の宛先へ送信する
- APSchedulerで毎日08:00に自動実行する
- 手動実行とログ確認で再実行・障害確認ができる

## 8. 今回やらないこと
- Web UI
- 複数ユーザー対応
- 認証、認可
- 複数分野設定
- HTMLメール
- クラウド本番運用
- 監視基盤、CI/CD、ジョブキュー

除外理由:
- 1本目のポートフォリオでは、構成の見栄えより完成率を優先するため
- 現時点で追加すると、実装難易度と説明範囲が広がりすぎるため

## 9. 成功条件
### 9-1. プロダクト成功条件
- ユーザーが指定した分野のニュースを取得できる
- 上位5件以内を要約して送信できる
- 毎日08:00の定期実行が成立する
- 失敗時にログで原因を確認できる

### 9-2. ポートフォリオ成功条件
- 外部API連携、AI要約、DB保存、メール送信、定期実行を説明できる
- 技術選定理由を「学習コスト」「実装容易性」「説明しやすさ」で説明できる
- Dockerで再現できる

## 10. KPI / 確認指標
| 指標 | 目標 |
|------|------|
| 1回の実行で取得する記事数 | 最大20件 |
| 1回の配信対象記事数 | 最大5件 |
| 定期実行頻度 | 1日1回 |
| 配信先 | 1件固定 |
| 処理完了目安 | 数分以内 |
| 完成目標期間 | 2週間から4週間 |

## 11. スコープ判断方針
- 判断基準の最上位は「一人で完成可能か」とする
- 次に「実装難易度が適正か」を見る
- その次に「ポートフォリオとして説明しやすいか」を見る
- 将来拡張性は維持するが、MVPで先に実装しない

## 12. 企画上の主要判断
| 項目 | 判断内容 | 理由 |
|------|----------|------|
| 中心機能 | バッチ処理中心 | 画面なしでも価値を示せるため |
| ニュース取得元 | NewsAPI | レスポンスが扱いやすく学習負荷が低いため |
| 要約方式 | OpenAI API | AI活用実績として説明しやすいため |
| 保存先 | SQLite | セットアップが簡単でローカル完結できるため |
| 通知方式 | SMTPメール | シンプルで結果が可視化しやすいため |
| 実行方式 | FastAPI + APScheduler | 手動確認と定期実行を同一アプリで扱えるため |
| 分野指定方式 | 設定ファイルまたは環境変数で1分野を事前指定する | MVPでは画面なしで実装負荷を抑えつつ、ユーザー指定要件を満たせるため |

## 13. 想定リスク
| リスク | 内容 | 企画上の対応 |
|------|------|--------------|
| スコープ膨張 | Web UIやクラウドまで広げたくなる | MVP対象外を明確に維持する |
| 外部API失敗 | NewsAPI、OpenAI API、SMTPの失敗が発生する | 失敗をログで追える設計を前提とする |
| 学習負荷集中 | Docker、SMTP、環境変数管理で詰まりやすい | 技術を増やさず、採用技術を固定する |
| 運用誤解 | ローカル停止中にジョブが動かない | 常時運用はMVP対象外と明記する |

## 14. 進め方
1. 企画概要で目的、価値、成功条件を固定する
2. 要件定義でMVP範囲を固定する
3. 基本設計でシステム構成と機能境界を定義する
4. 詳細設計で実装単位へ分解する
5. アーキテクチャ設計で非機能、運用、将来拡張を整理する
6. 実装ではMVP必須機能から順に着手する
