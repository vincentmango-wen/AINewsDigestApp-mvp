# MVP要件定義

## 1. MVPの位置づけ
- このMVPは、FocusDigestの最小完成版である
- ニュース取得、記事選定、AI要約、メール送信、定期実行、保存の一連の流れを、一人で最後まで実装して動作確認できる範囲を担う
- このMVPでは「バックエンド処理が毎日自動で動き、要約結果がメールで届く」ことを完成条件とする
- Web UI、ユーザー管理、複数配信先管理、運用監視の高度化はMVP対象外とする

## 2. MVPの目的
- AI APIを使った実用的なアプリを1本完成させる
- Pythonで外部API連携、データ保存、バッチ処理、メール送信を実装できることを示す
- 面接で「どの入力を受けて、どの処理を行い、何を出力するか」を説明できる成果物にする
- 一人で2週間から4週間で完成できる範囲に機能を限定する
- 後続のWeb UI追加や配信条件拡張につながる土台を作る

## 3. MVPのスコープ
### 3-1. 対象機能
- 指定カテゴリのニュース取得
- 取得記事の保存
- 上位記事の選定
- OpenAI APIによる要約生成
- 要約結果のメール送信
- 日次の定期実行
- 実行結果とエラーのログ出力

### 3-2. 対象外機能
- Web UI
- ユーザー登録、ログイン、権限管理
- 複数ユーザーごとの配信設定
- カテゴリの動的追加画面
- ニュース本文のスクレイピング
- 高度な重複除去アルゴリズム
- 要約品質の自動評価
- 多言語対応
- クラウド本番運用
- 管理画面
- モバイル通知
- 添付ファイル付きメール
- 対象外理由：初回ポートフォリオとしては実装量が増え、完成率が下がるため

## 4. 想定利用シナリオ
1. 開発者がアプリに収集対象の分野を1つ設定する。例として「AI」「金融」「セキュリティ」などを指定できる
2. スケジューラが毎日朝8時にバッチ処理を起動する
3. アプリがニュースAPIから指定分野の記事一覧を取得する
4. 取得した記事メタデータをSQLiteに保存する
5. 保存した記事から、公開日時が新しく、タイトル重複がない上位5件を選定する
6. 各記事のタイトルと説明文をOpenAI APIに渡して日本語要約を生成する
7. アプリが5件分の要約を1通のメール本文に整形する
8. 指定した1つのメールアドレスへ送信する
9. 成功時は実行日時、取得件数、送信結果をログに残す
10. 失敗時は失敗した処理内容をログに残し、その日の処理を終了する

## 5. 機能要件

### ニュース取得
- 目的：要約対象となるニュース記事一覧を外部APIから取得する
- 入力：ユーザーが事前設定した分野名1件、取得件数上限20件、NewsAPIのAPIキー
- 処理：NewsAPIの該当エンドポイントへリクエストし、指定分野に関連するタイトル、説明文、URL、公開日時、配信元を取得する
- 出力：記事一覧データ
- 正常系：APIレスポンスから20件以内の記事を取得し、後続処理へ渡す
- 異常系：APIキー不正、通信失敗、レスポンス不正時はエラーログを出力し、その回の処理を中断する
- MVPでの簡略化：取得元はNewsAPIの1サービスのみに固定する。分野指定は1回の実行につき1件に固定する
- 実装優先度：最高

### 記事保存
- 目的：取得した記事を後続処理と再実行確認のために保存する
- 入力：記事一覧データ
- 処理：SQLiteに記事情報を保存する。URLを一意キーとして重複登録を防ぐ
- 出力：保存済み記事レコード
- 正常系：新規記事が保存され、既存記事は重複登録されない
- 異常系：DB接続失敗、テーブル不整合、INSERT失敗時はエラーログを出力し、その回の処理を中断する
- MVPでの簡略化：保存対象は記事メタデータと要約結果のみとする。全文保存は行わない
- 実装優先度：最高

### 記事選定
- 目的：要約対象を少数に絞り、APIコストとメール可読性を抑える
- 入力：保存済み記事、上位件数5件
- 処理：公開日時の新しい順に並べ、URL重複を除外し、上位5件を選ぶ
- 出力：要約対象記事5件以内
- 正常系：5件以内の記事が選定される
- 異常系：記事が0件の場合は「配信対象なし」としてログ出力し、メール送信は行わない
- MVPでの簡略化：スコアリングは公開日時順のみとする。人気度分析や埋め込み検索は行わない
- 実装優先度：高

### AI要約
- 目的：記事の内容を短く整理し、メールで読める形に変換する
- 入力：記事タイトル、記事説明文、記事URL
- 処理：OpenAI APIへ要約プロンプトを送信し、日本語で2文から3文の要約を生成する
- 出力：記事ごとの要約テキスト
- 正常系：各記事に対して日本語要約が生成され、DBへ保存される
- 異常系：APIエラー、タイムアウト、入力不足時は当該記事の要約を失敗扱いとし、他記事の処理は継続する。全件失敗時はメール送信を中止する
- MVPでの簡略化：要約入力は本文ではなくタイトルと説明文のみとする。要約形式も固定文面とする
- 実装優先度：最高

### メール送信
- 目的：要約結果を利用者へ届ける
- 入力：要約済み記事一覧、送信先メールアドレス1件、SMTP設定
- 処理：件名と本文を生成し、1通のテキストメールとして送信する
- 出力：送信結果
- 正常系：送信成功ログを記録する
- 異常系：SMTP認証失敗、接続失敗、送信失敗時はエラーログを出力する。要約結果はDBに残す
- MVPでの簡略化：送信先は1件固定、本文はプレーンテキスト固定、HTMLメールは扱わない
- 実装優先度：最高

### 定期実行
- 目的：手動操作なしで毎日同じ処理を実行する
- 入力：実行時刻「毎日08:00」
- 処理：APSchedulerで日次ジョブを起動し、ニュース取得からメール送信までを順番に実行する
- 出力：定期実行されたバッチ処理
- 正常系：指定時刻に1回実行される
- 異常系：ジョブ起動失敗時はアプリ起動ログに失敗内容を出力する
- MVPでの簡略化：実行条件は1日1回固定とする。管理画面からの変更機能は持たない
- 実装優先度：高

### ログ出力
- 目的：実行結果と失敗箇所を確認できるようにする
- 入力：各処理の実行状態、件数、例外情報
- 処理：開始、終了、取得件数、要約件数、送信結果、例外内容をログファイルへ出力する
- 出力：テキストログ
- 正常系：1回の実行ごとに処理結果が記録される
- 異常系：ログ出力失敗時は標準出力へエラーを出す
- MVPでの簡略化：外部監視サービス連携は行わない。ローテーションも日次1ファイルで十分とする
- 実装優先度：高

## 6. 非機能要件
- 実行方法：ローカル環境またはDocker環境で1コマンド起動できること
- 可用性：24時間連続稼働は要求しない。日次バッチが起動し、1回の処理が完了することを重視する
- 保守性：処理単位を「取得」「保存」「選定」「要約」「送信」に分け、責務を分離する
- セキュリティ：APIキー、SMTPパスワード、OpenAI APIキーは環境変数で管理し、ソースコードへ直書きしない
- コスト制約：1日1回、上位5件、1記事あたり短文要約とし、OpenAI API利用料を低く抑える
- ログ・障害対応の最低ライン：失敗した処理名、発生時刻、例外内容をログで確認できること。再実行は手動コマンドで行えること

## 7. MVP時点の技術選定

| 項目 | 採用技術 | 理由 |
|------|----------|------|
| 言語 | Python | 学習コストが低い。API連携とバッチ処理の実装が速い。面接で処理の流れを説明しやすい |
| Webフレームワーク | FastAPI | 学習コストが低い。将来API化しやすい。Python製バックエンドとして説明しやすい |
| ニュース取得 | NewsAPI | 学習コストが低い。レスポンス形式が扱いやすい。外部API連携の説明がしやすい |
| AI要約 | OpenAI API | 学習コストが低い。AI活用実績として伝わりやすい。要約機能の中核として説明しやすい |
| データベース | SQLite | 学習コストが低い。セットアップが簡単。ローカル完結で説明しやすい |
| メール送信 | SMTP | 学習コストが低い。追加サービス契約が不要。送信処理の仕組みを説明しやすい |
| 定期実行 | APScheduler | 学習コストが低い。Python内で完結する。cronよりアプリ内の流れを説明しやすい |
| 実行環境 | Docker | 学習コストはあるが最小限で済む。環境差異を減らせる。ポートフォリオとして再現性を説明しやすい |
| ログ | Python logging | 学習コストが低い。標準機能で十分。障害時の確認方法を説明しやすい |

## 8. 完成条件
- ユーザーが指定した分野のニュースを1回の実行で取得できる
- 取得した記事がSQLiteへ保存される
- 保存済み記事から上位5件以内を選定できる
- 各記事について日本語要約を生成できる
- 要約結果を1通のメールとして送信できる
- APSchedulerで毎日08:00に処理が起動する
- 成功時と失敗時のログが確認できる
- APIキー未設定時に異常終了し、原因がログで分かる
- Docker環境で起動し、同じ処理を再現できる

## 9. MVPで切り捨てるもの
- Web UI
理由：画面実装まで広げると、バックエンド完成前に工数が分散するため
- 複数ユーザー対応
理由：認証、設定管理、配信先管理が追加され、初回ポートフォリオとして重い
- 実行時の分野変更UI
理由：MVPでは設定ファイルまたは環境変数で分野を事前指定する方式に絞るため
- ニュース本文取得
理由：サイトごとの取得差異が大きく、失敗要因が増えるため
- 高度なランキング
理由：評価軸設計と検証に時間がかかるため
- HTMLメール
理由：見た目は良くなるが、MVPの価値は処理の一連実装にあるため
- クラウドデプロイ
理由：AWS学習と運用設定が追加され、完成時期が遅れるため
- 学習価値は高いがMVPから外すべきもの：認証、監視基盤、ジョブキュー、PostgreSQL、CI/CD
理由：面接映えはするが、1本目で完成率を下げるため

## 10. 想定リスク
- 技術リスク：Docker、APScheduler、SMTP設定で初回のつまずきが発生しやすい
- API依存リスク：NewsAPIの無料枠制限やOpenAI APIのレスポンス失敗で処理が止まる可能性がある
- 学習コストリスク：FastAPI本体より、環境変数管理、Docker、メール認証まわりで理解負荷が上がる
- 運用リスク：ローカル常駐前提ではPC停止中に定期実行されない。MVPでは「毎日自動配信の体験確認」を優先し、常時運用は対象外とする
